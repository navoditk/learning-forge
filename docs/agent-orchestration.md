## Actual-model independence

On 2026-10-10 the owner approved updating the native Codex `forge-reviewer`
role to `gpt-6.1-sol`, available in the owner's current client. This supersedes
the earlier `gpt-6-sol` reviewer mapping for future reviews only; historical
review identity and availability evidence below remain unchanged. The parent
default and expert/implementer roles are unchanged. Reasoning effort remains
client-controlled. Restart or reload an existing client before dispatch and
verify effective worker selection; an unavailable model blocks dispatch rather
than authorizing silent fallback.

Before a review starts, record the executor and reviewer tool, actual model ID,
model family, revision/commit or patch identifier, and how identity was verified
(client metadata or confirmed model selection, not the model's self-report).

- In a multi-provider environment such as Copilot, required independent
  reviews use a different actual model family from the executor.
- In single-provider Claude Code or Codex, routine reviews may use a different
  actual model in a fresh context. Claude Sonnet implementation with Opus
  review, or GPT Mini implementation with GPT Sol review, are reduced-diversity
  options, not cross-family review.
- Critical safety, privacy, scoring/mastery, authorization, held-out content,
  or destructive migration changes always require cross-family review.
  Hand the revision to another tool/provider if necessary.
- A new session, different reasoning effort, or changed prompt on the same
  model is not model diversity. Unknown IDs/families mean `UNVERIFIED`, not
  compliant. Report the block; do not mark the review gate complete.
- Reviewers re-derive conclusions from artifacts and tests, not executor
  self-evaluation. They do not edit the reviewed patch or approve release.
  A changed patch needs review of the changed scope.

The single-provider exception was explicitly approved on 2026-10-09. If a
premium executor cannot obtain a different capable reviewer within one
provider, transfer review rather than downgrade a high-risk review.

## Author and reviewer accountability

Apply this contract to design, content and implementation packets in every
client. It strengthens handoff evidence, not permission to run extra tools,
spawn self-review agents, broaden scope or bypass independent/human gates.
Use the existing packet, evidence bundle and review report; do not create
another planning document for the checklist. Instructions improve consistency
but do not guarantee model correctness.

### Author handoff: demonstrate, do not assert

Before freezing, return a compact requirements-to-evidence table: each owned
requirement, artifact location, acceptance case and actual result, including
untested or blocked claims. Exercise authorized positive, negative and exact
boundary cases. In document-only work, manually derive concrete examples and
counterexamples against the proposed rules; do not run unauthorized runtime
tests or call an example executable evidence.

Check contradictions across schemas, examples, error precedence, projections,
limits, versions and acceptance criteria. A correct response must be
representable; a leakage assertion must not reject a required public field;
a claimed maximum needs a valid example or must be labelled conservative.
Keep new rules minimal and remove redundant restatements. Do not submit an
artifact known to violate its own required acceptance cases.

For corrections, retain every finding ID and return:

| Finding            | Root cause                                    | Changed locations                | Before/after evidence                         | Regression check                                 | Status                       |
| ------------------ | --------------------------------------------- | -------------------------------- | --------------------------------------------- | ------------------------------------------------ | ---------------------------- |
| Existing report ID | Why the defect occurred, not just the symptom | All coupled rules/examples/tests | Concrete derivation or authorized test result | Earlier fixes and directly affected requirements | Resolved, partial or blocked |

"Resolved" requires evidence for the original counterexample and a valid
positive control, not a rewritten paragraph or passing formatting. Inspect
all references to the corrected rule, preserve earlier fixes and freeze exact
bytes only after this self-audit. The author does this directly; it is not
independent review and does not justify another model call.

### Reviewer handoff: comprehensive first pass, bounded follow-up

The first review covers the whole approved scope and returns all verified
findings together, plus a coverage summary listing checked requirements and
unverified areas. Do not drip-feed known findings. Every finding names the
violated approved requirement or concrete correctness/safety failure,
file/lines, counterexample, severity/confidence and acceptance condition for
closure. Separate defects from missing evidence, optional preferences and
new product requests. Do not turn stylistic preference into a blocking gate.

Re-review the diff, original counterexamples, closure evidence and directly
coupled regressions; do not restart an unrelated full audit. New real defects
must still be reported. Classify each follow-up finding as:

- **Unresolved:** the prior counterexample still fails or closure is incomplete.
- **Regression:** the correction introduced or restored the failure.
- **First-pass miss:** present in previously reviewed scope but not reported.
- **Newly observable:** exposed by changed scope or previously unavailable evidence.

Retain IDs for unresolved findings. For a first-pass miss, explain why it was
missed and the specific check that now detects it. Do not infer reviewer
failure for a genuinely newly observable issue. Optional polish is follow-up
work unless an existing accessibility/product requirement makes it necessary.
Only the appropriate human can accept residual risk; reviewers cannot downgrade
a real correctness/safety issue merely to finish a round.

### Integrator control: stop automatic review loops

Require the evidence/closure table before paid independent review. If missing,
return one consolidated request within the same approved scope; do not launch
a review worker just to discover missing handoff fields. Preserve frozen
artifacts and record rounds in the existing task packet:
author/model/hash, blocker/major/minor counts, unresolved/regression/miss/new
classification, validation limits and the learner-visible increment being
unblocked. Do not invent time or cost metrics.

If a blocker/major remains after a correction and its re-review, pause
automatic dispatch. Record a short cause analysis and corrective action in
the packet: incomplete fix, contradictory/oversized contract, missed review
coverage or unavailable evidence. Use a concrete reproducer/derivation and
consolidated correction scope; ask the owner if scope or an approved choice
must change. Then resume the eligible role, not an unapproved replacement
model or another broad review. This is an escalation checkpoint, not a
hard round cap: unresolved safety/correctness gates still block release.

### Delivery exit rules

Target one comprehensive first review, one consolidated correction and one
changed-scope verification per coherent frozen increment; this is the normal
path, not a promise or a cap that permits shipping defects. Freeze the owned
scope and acceptance criteria before review. New feature requests and
optional improvements go to the backlog, not new acceptance criteria for
the in-flight packet.

Do not schedule an additional assurance review of unchanged bytes once the
required findings and evidence are closed. If a required finding of any
severity survives its correction and verification, use the same root-cause
checkpoint above before another dispatch. Do not buy another broad review
to compensate for an incomplete author self-check.

The reviewer names which findings prevent readiness and why, rather than
making every minor or preference an automatic new round. Eligible residual
risks may be presented together for explicit human disposition; required
safety, privacy, authorization, scoring, content and accessibility gates
cannot be silently waived or downgraded. After the scoped review is ready,
route directly to the existing acceptance/integration gate and next approved
learner-visible increment. Avoid extra "review the review" agents.

Accept existing completed reviews without retroactive re-audits. For an
in-flight correction, attach this lightweight closure evidence at its next
freeze; do not mutate the historical frozen inputs. Once required findings
are closed, route to the existing human/integration gate and stop adding
speculative prerequisites. Review throughput serves delivery; it is not a
substitute for implementing the next approved learner-visible increment.

## Delegated model sign-off

D-207 (owner-revocable) lets a verified cross-family reviewer sign off two
gate classes for Claude-authored work instead of a separate owner reply:
in-scope dispositions where reviewer and integrator recommend the same
option, and per-item acceptance of practice items with deterministic
structured answers that the reviewer re-solves and the frozen harness
passes. The integrator records each sign-off as its own decision, sends the
owner a summary with about 3 random spot-check items, and withdraws any item
the owner rejects within 7 days. Disagreement, scope widening, teaching or
held-out content, private access, paid providers, manual accessibility,
production facts, privacy, spending, destructive migrations, D-61 exceptions,
registration/exposure, commit, push, deployment and release remain human
gates. Same-family or unverified review never qualifies.

D-212 (owner-revocable) widens this: every internal, reversible approval or
owner-choice gate (content acceptance of any role, D-61 exceptions, scope
approvals, dispositions, owner-choice design questions, risk acceptances,
local patch application) is decided by the verified cross-family reviewer,
given the options, evidence and integrator recommendation. The integrator
records each decision separately and lists it in PROGRESS for later owner
override; no veto window is required. Paid-provider runs and keys, manual
assistive-technology passes, production facts, production/learner/private
data access, commit, push, deployment, release and production migrations
stay with the owner. Agents do not stop for them: they continue other
eligible work and report what awaits the owner.

## Batched human approvals

Default to one consolidated approval request for related decisions that are
ready for the appropriate human owner. Before asking, collect the ready
choices in the current packet and directly related approved scope; do not
prompt one by one when their options and evidence can already be presented
together. Do not wait for an unrelated or blocked decision to become ready,
reopen completed approvals, or bundle the entire backlog.

Use the existing packet and decision register, not a new approval document.
Present a compact table containing each decision ID, recommended option,
material tradeoff, exact scope/artifact revision where applicable, readiness
evidence and what it authorizes. State what remains excluded and any
dependencies. Offer acceptance of all listed recommendations, a subset, or
overrides in one interaction. A clearly framed batch may be accepted with one
reply; do not demand a separate confirmation for each unchanged choice.
If the response or batch is ambiguous, clarify only the affected decisions
and leave them pending.

Batching requests does not merge authorization gates. Design acceptance,
patch application, bounded implementation, private-content access, migration,
paid-provider use, deployment and release remain separately identified
permissions. Each included gate must have its own required evidence,
eligible approver and exact scope; do not obtain blanket approval for future
unreviewed artifacts. A dependent gate whose evidence does not yet exist
stays pending. If an approved choice changes reviewed bytes, obtain the
required changed-scope review before crossing the next artifact gate.

Record the human response and disposition against each approved decision,
including scope, revision and conditions where applicable. Route only work
explicitly authorized by that response. Approval of this batching procedure
does not approve any pending product choice or execution packet.

## Parallel work graph

For each program:

`research -> independent research review -> human source approval ->
authoring -> independent content review -> human content approval ->
integration`

UI design can run beside research against synthetic fixtures; serving real
curriculum waits for its approval and the applicable progression gates.
Implementation review follows the exact completed patch; integration follows
review and validation. Human product/content/policy/privacy/release decisions
remain human decisions. An LLM judge supplies structured advisory findings,
never authoritative learner scores or permission to bypass a gate.

Research for different programs is independent. Each reviewer receives only
its program's source dossier and reviewed revision. Shared schema, policy,
program-registry, main-page UI, and migration work is NOT independent: assign
one owner and serialize those edits.

1. Coordinator defines a task packet: ID, program/scope, approved inputs,
   expected artifacts, owned files, prerequisites, actual model allocation,
   acceptance criteria, test commands, and stop conditions. Request a fleet
   explicitly; a documented plan is not permission to launch all backlog work.
2. Use isolated git worktrees for writers. Research workers write separate

   One integrator publishes the approved source register and `PROGRESS.md`.
   Review workers are read-only.
3. Launch only ready, independent tasks. No fixed pool of agents reused across
   unrelated curricula. Use the minimum workers appropriate to the batch;
   preserve user ceilings and report cost/quota constraints, never invent
   unlimited concurrency.
4. Pass scoped files and acceptance criteria, not whole chat histories or the
   entire progress log. Return concise findings and artifact references.
   Load only the needed skill/playbook; avoid duplicated parent investigation.
5. After each completion, checkpoint task status, revision, evidence, model
   provenance, findings/disposition, blockers, and next task. Failed or
   interrupted tasks remain incomplete and must not look like success.
6. Integrator checks shared contracts and collisions, applies reviewed work,
   runs applicable synthetic validation, and updates durable status. Never
   run shared-database tests concurrently without isolated databases.
7. Use Copilot fleet facilities or native client orchestration when available;
   otherwise use separately launched sessions/worktrees and the same packets.
   No vendor-specific orchestration is required to understand or resume work.

### Ownership with several terminals open

- The human designates one integrator for the active batch. Other terminals
  are scoped workers or read-only reviewers; idle terminals are not owners.
- Before writing, acquire an advisory atomic directory claim in the common
  Git metadata directory (resolve it with
  `git rev-parse --path-format=absolute --git-common-dir`).
  Store claims under `agent-claims/`: `integrator.lock` for the integrator,
  `<task-id>.lock` for a worker. Acquire with a single `mkdir`, not a
  check-then-create; failure means **do not write**. Record task, client/model,
  role, worktree, owned paths and start time in that claim, without secrets.
  The integrator claim does not block independent workers' task claims.
- Claims are advisory coordination for cooperating local sessions, not
  authorization, a distributed lock or protection against other editors.
  The packet's owned paths and existing repository rules still govern.
- Each writer uses a distinct worktree and explicit owned paths. Shared
  schemas, registries, source indexes, decision matrix and integration/status
  edits are serialized by the integrator. Workers return a patch/report;
  they do not update shared PROGRESS/handoff files. A reviewer must not read
  a patch while its author is changing it.
  Before assignment the integrator checks active claims for overlapping
  owned paths; different task IDs do not make shared-file edits independent.
- The author marks the artifact frozen and stops writing before review.
  Corrections reopen that same worker role; freeze and repin afterward.
  Reviewers report without editing, installing or mutating the worktree.
- After checkpointing, release only the claim the session owns; remove its
  named metadata files and then the empty directory. Never auto-steal claims
  by age. For a stale claim, the human confirms the former owner has stopped
  before authorizing targeted cleanup. Never clear other claims or worktrees.
- Integration checks the frozen hash and current base, applies only the
  reviewed patch, resolves collisions without overwriting existing work, and
  validates the integrated tree. Shared database/browser/build jobs must
  not run concurrently against shared state; use the documented synthetic
  isolation and preserve any required approval.

### Durable task packet

The integrator maintains one small packet per actual assigned task under
`docs/agent-handoffs/<task-id>.md`, referenced by the resume index. This
location is for safe task metadata, never raw child data, credentials,
private assessment items, full logs or proprietary source text. Do not create
packets for every hypothetical backlog item.

Every packet records:

1. Task ID, phase (`SCOPING`, `IMPLEMENTING`, `AWAITING_REVIEW`,
   `CHANGES_REQUESTED`, `AWAITING_HUMAN`, `READY_TO_INTEGRATE`, `DONE` or
   `BLOCKED`), claimed role/client/model and owned files.
2. Exact approved scope and approval citations; prohibited actions and
   remaining human gates. Planning permission is not implementation approval.
3. Main HEAD, worktree HEAD and **effective uncommitted baseline**: an
   allowlisted overlay/patch and untracked inputs with file hashes if needed.
   `git diff` alone omits untracked files. New worktrees and fresh clones
   do not inherit the coordinator's uncommitted state.
4. Required docs and artifacts, repository-relative where possible; frozen
   patch/specification hash, changed-file list and original author model
   provenance. Include enough evidence to recreate the result locally.
5. Exact commands and results, what was not run and why, findings and
   dispositions. Do not infer runtime correctness from a proposal.
6. One bounded next action, its eligible client/model, stop condition and
   copy-paste prompt.

Large local patches and sanitized command output may live under
`agent-handoffs/` in the resolved common Git metadata directory; record their
resolved paths and hashes in the packet. They are local artifacts, not in
GitHub and not transferred with a clone. Do not relocate or delete existing
session artifacts until their needed contents have been verified in the
new handoff. If moving machines, the human explicitly approves either a
reviewed commit/push or transfer of an allowlisted non-sensitive patch/input
bundle. Never copy `.env`, whole session folders or private banks.

### Required terminal-switch message

End a role with one of these labels and fill in every field:

```text
SWITCH TO: <Claude Code or Codex>, <configured forge role>
ROLE: <read-only reviewer / original-author corrections / integrator>
TASK: <task ID and packet path>
ARTIFACT: <frozen patch/spec path and SHA-256>
DO NOW: <one bounded action>
STOP AFTER: <report / corrected patch / integrated validation>
START: <plain claude or codex; "continue" if idle>
RECOVERY PROMPT: <only if instruction discovery fails; reference packet and authority>
```

For an undecided parameter, write `WAITING FOR HUMAN APPROVAL`, identify only
the consumed decision IDs and recommendation, and stop before implementing
them. For a missing artifact/model/permission, write `BLOCKED`, identify the
missing evidence and recovery action. Do not say "switch" as a substitute for
an approval. The human runs the terminal command; agents cannot transfer live
chat context or switch another client's account/session automatically.

### Wrong-client and quota-conserving intake

For continuation, `docs/coding-agent-handoff.md` supplies the ordered relay
and the active packet supplies its current phase and next client/role.
Check both before claiming work or dispatching a native agent. A mismatched
client reports the terminal-switch message above and stops; it does not
skip ahead, reassign itself, redo the author's work or substitute a
same-family review. Human gates stop either client. Running claims are
wait conditions, never grounds for duplicate work or automatic cleanup.

Historical documents in an isolated baseline are not the live routing
index. Read the control checkout's current index/packet (the repository
from which the terminal was launched); use the isolated baseline only for
the pinned implementation/specification being reviewed.

At a quota-conserving checkpoint, finish/freeze the bounded in-flight role,
persist allowlisted evidence in common Git metadata and assign the next
native role before credits run out. Do not consume the remainder on a fleet,
repeat research or speculative tasks. Copilot quota does not reveal or
govern native Claude Code/Codex quota. Markdown instructions route cooperating
agents; they do not enforce permissions, switch accounts/models or prove
native role discovery.

Configured read-only reviewers remain read-only. Their named parent/
integrator performs authorized synthetic validation separately, then supplies
frozen source and independent results. Permission failures are recorded as
missing evidence, not solved by weakening the reviewer's sandbox.
