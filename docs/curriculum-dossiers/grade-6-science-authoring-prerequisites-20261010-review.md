## Findings

### SCI6-P1 — Required core principle/impact coverage is allocated only to depth

**Severity: major. Confidence: high.**

**Location:** reviewed proposal lines 437–453.
**Rule:** inherited core-plus-depth scope, approved dossier lines 124–129
and 161–166; SCI6-S01, MS-ETS1-1.

The first packet assigns two core records to requirement classification and
solution checks, but explicitly assigns identification of a relevant
scientific principle or people/environment impact to depth. That is part
of the governing design-problem expectation, not inherently enrichment.
Meanwhile the packet's partial-assessment claim includes principle/impact
identification without distinguishing this depth-only observation from core.
The proposal also needs to distinguish recognizing supplied requirements
from defining precise requirements for a provided problem.

**Smallest safe remediation:** keep the first component skill partial,
state exactly which core components its two core records evidence, and
explicitly retain precision and principle/impact treatment in subsequent
core coverage. Alternatively redistribute the bounded records if both can
fit. Use depth for richer comparison or trade-off reasoning, not the only
encounter with a required core component. Do not demand full MS-ETS1-1
coverage in this three-record increment or physical stakeholder work.

**Acceptance expectation:** core coverage notes identify what is evidenced
now, what remains core later, and what depth extends; no depth-only response
is necessary to establish a core component claim.

### SCI6-P2 — Proposed cross-day/cross-format mastery rule is not executable

**Severity: major. Confidence: high.**

**Location:** reviewed proposal lines 233–237, 274–276, 448–453, 513–515.
**Rule:** evidence/policy separation, no practice-completion mastery, and
traceable parent claims (`docs/05-data-and-student-model.md:47–71`).

The proposal refers to multiple observations across time/formats as existing
structured rules “declared” in `masteryCheckRule`, then proposes two correct
responses on different days and in two formats. That field is only a bounded
string (`src/contracts/curriculum.ts:63`), not an executable contract.
`MasteryObservation` has no response-format field, and
`aggregateMastery` counts assistance-zero observations without requiring
distinct days or formats (`src/progression/mastery.ts:3–15,80–92`).
The Science profile's numeric defaults do not implement the proposed rule.
Nor does owner confirmation of those defaults establish validity.

The learner-serving Phase 1 path is a separate concern: one correct
same-session independent check can set `independentDelayedCheck`
(`src/phase1/service.ts:350,438–450,645–677`). This is inspected pre-existing
behavior, not a new regression; it is nevertheless not the promised Science
cross-day/cross-format rule.

**Smallest safe remediation:** label the proposed rule advisory pedagogy,
not shipped enforcement. Explicitly prohibit first-packet Science mastery,
“Secure”, full-PE and hands-on claims; preserve only bounded, traceable
practice/component evidence. Before Science learner release, verify that
all relevant learner/parent/planner projections honor that cap, or separately
implement and review the evidence policy. Do not require a new mastery engine
merely to draft pending practice records in isolation.

**Acceptance expectation:** the specification distinguishes deterministic
item correctness from mastery; threshold approval alone cannot activate
claims. Any later mastery implementation tests distinct eligible
observations, assistance, temporal separation, response formats, core/depth
separation and the exact component claim being reported.

### SCI6-P3 — Pending content filtering does not hide draft skill/mastery claims

**Severity: major. Confidence: high.**

**Location:** reviewed proposal lines 153–157, 479–480, 500–505, 522–523.
**Rule:** D-58's reviewed public projection and the proposal's pending
human-approval boundary.

The cited item filter is correct:
`src/content/publication.ts:16–22` removes pending and held-out-role items.
But the generator independently iterates all `skillCatalog` entries
(`scripts/generate-curriculum-site.ts:170–176`), counts their standards and
skills (lines 189–194), and renders “Mastery check” and “What mastery looks
like” from skill metadata (lines 140–150). An unavailable program with skills
is explicitly rendered as an authored draft (lines 205–223,270–278).

Thus the first pending Science skill plus its pending practice records would
hide the practice prompts while still publishing unapproved skill evidence,
mastery prose and standards-coverage claims. Existing sentinel tests inject
content, not an unpublished skill
(`tests/content/held-out.test.ts:8–26`). This is a latent public-draft
projection gap relevant to the proposed increment, **not evidence of exposed
child data, a present Science item leak, or a newly introduced code bug**.
An independent current-main, in-memory unavailable-Science skill sentinel
confirmed that `buildBody([])` exposes its title, evidence, mastery rule and
standard even with no publishable content. No sentinel file was authored.

**Smallest reusable remediation:** for this unavailable first program, reuse
the existing program availability boundary to keep its skill details out of
the public site and its coverage statistics. Preserve the “Coming soon”
placeholder. If approved public draft skill previews are intentionally wanted,
that needs a separately reviewed scope/projection rather than an incidental
content-only filter. No new skill-review schema or bespoke Science renderer
is needed for the smallest solution.

**Acceptance expectation:** a synthetic unavailable-program skill with
pending practice exposes none of its title/code, evidence, mastery rule or
standards contribution in public details/statistics, while reviewed available
programs render unchanged. This blocks merge into automatic public
publication, not isolated drafting under an otherwise valid authorization.

### SCI6-P4 — Gate list conflates implementation choices with owner decisions

**Severity: minor. Confidence: high.**

**Location:** reviewed proposal lines 459–460, 498–526.
**Rule:** issue-sized increments; inherited approved scope and reuse of
existing engineering invariants.

O2/O3/O7 are implementation selections, not three independently necessary
product approvals. Similarly, accessible tables and choice radios are useful
later features, but fully supplied small text data and exact-response choices
already have an accessible path. G5 option B is not a structural prerequisite
to every future held-out item. Several §12 tests exercise existing invariants;
they should demonstrate preserved behavior, not all be required to fail before
an implementation change.

**Smallest safe remediation:** distinguish a small owner authorization
bundle from serialized engineering work and later-release capabilities.
Keep conditional requirements conditional; do not invent a new assessment
bank gate for diagnostic choice metadata.

**Acceptance expectation:** an implementer can identify what blocks drafting,
what blocks catalog integration/publication, and what blocks learner/mastery
release without seeking renewed approval of settled scope.
