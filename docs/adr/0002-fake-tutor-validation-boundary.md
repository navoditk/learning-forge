# ADR-0002: Validate tutor output at the orchestration boundary

- Status: Proposed
- Date: 2026-09-05
- Decision owner: Product/engineering owner
- Related issue: LF-0.6

## Context

Tutor output is generated by a model boundary that cannot be trusted to obey
TypeScript types or server policy. LF-0.6 needs to exercise malformed output,
answer leakage, unauthorized moves, repair, and fallback without provider
credentials or learner data.

## Decision

The provider-neutral `TutorModel.generateMove` and scoring methods return
`unknown`. The tutor harness parses generated moves with the existing Zod
schemas, applies server-controlled authorization, retries once for repair, and
returns a curated fallback when validation still fails. Only validated moves
may advance policy state. Fallbacks never advance mastery.

The Phase 0 fake adapter produces deterministic, generic prompts. It does not
include canonical answers or claim mastery evidence. Trace records use the
existing metadata contract and redact learner text by default.

## Alternatives considered

- Trust the TypeScript return type: rejected because provider responses are
  runtime data and must be validated at the boundary.
- Let the model select the next policy state: rejected because authorization,
  answer protection, and mastery transitions are server-controlled.
- Add a real provider: deferred because child-data terms and credentials are
  not approved for Phase 0.

## Consequences and reversal signals

This adds a small validation/orchestration seam and makes malformed provider
responses testable. It requires adapters to return runtime data rather than
pretend that a type annotation proves validity. Revisit if a shared provider
SDK supplies independently verified structured decoding, but retain the
server-side policy and leakage checks.

This ADR does not approve provider use, child-data retention, policy defaults,
or release readiness; those remain subject to ADR-0001 and human review.
